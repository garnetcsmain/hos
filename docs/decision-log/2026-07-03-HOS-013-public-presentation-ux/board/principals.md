# Principals Review: HOS-2026-013

## My Recommendation

🟡 **RESHAPE.** The proposal is mostly consistent with HOS's principles, and three of its five pieces are clean. But its centerpiece — the animated *public* pulse board — is the one place the design leans on interface where the principles demand information, and its two load-bearing honesty/minimization claims (the "animations bind 1:1 to real events" guarantee and the "PII-free by construction, enforced by serializer tests" contract) each contain a specific logical gap that must be closed before build, not after. Fix those and the split verdict is:

- **D2 (Mi tablero), D3 (onboarding), D5 (console ergonomics): 🟢 GREEN.** Pure information/usability, no gate, no PII, and they are the actual value for the actual user.
- **D1 coordinator-gated board: 🟢 GREEN** — situational awareness behind the existing gate, honest by real-event binding.
- **D1 public variant (incl. landing demo mode): 🟡 RESHAPE** — permissible in principle, but as written it substitutes spectacle for information and rests its honesty on a label that fights an animation. Ship a static labeled snapshot, not synthetic motion, until the gate opens.
- **D4 (Ver como): 🟢 GREEN, conditional** on one binding invariant (server-side re-fetch, never client-side masking).

Option C is a correct 🔴 KILL (bypasses a standing gate). Option B is a correct rejection as an *end state*.

## Principles Alignment

- **AI recommends, people decide**: ALIGNED. Nothing here dispatches or acts against a person; the board visualizes state transitions humans authored. The proposal correctly fences off scope creep toward volunteer dispatch (risk #6) as a CLOSED door this may not become a side entrance to. Keep that fence load-bearing.

- **Information before interfaces**: **VIOLATED for the public D1, ALIGNED for everything else.** This is the core tension and the proposal half-admits it (its own User question asks "which of the four is the actual adoption driver"). For a *coordinator*, a live activity view IS information — situational awareness. For the *public/affected* user, the stated job of the pulse board is "understand in seconds that the system is alive" — that is a trust/marketing goal, not information delivered to the person who needs water. The family in Catia on a $60 Android needs D2 (Mi tablero) + search, not a sci-fi animation; the animation is interface *about* the system standing in for information *from* the system. D2/D3/D5 are correctly information-first. The animated public board inverts the ordering for the one audience the principle most protects. It is not forbidden — but it is enhancement, and the principle says it ships *after* the information layer, not as the headline.

- **Trust & honesty layer**: ALIGNED for real-event binding; **CONDITIONAL (leaning VIOLATED as framed) for demo mode.** See Logic Check #1 for the non-sequitur. Short version: the honesty guarantee the proposal offers ("animations bind 1:1 to a REAL recorded event") is *true of the coordinator board and false of the public demo* — demo mode is defined by synthetic data with no real event behind the motion. Its honesty therefore rests entirely on the label "demostración," on the highest-traffic, lowest-context surface HOS has, viewed by a distracted person on 3G who did not come to read fine print. Labeled fiction can be honest fiction. But the proposal must not claim demo mode is covered by the 1:1 binding — it is the exact exception to it — and it must hold the label to a bar a hostile screenshot cannot strip (a still frame of the animation, shared to WhatsApp without the label, must not read as "this is happening now").

- **Data minimization / least-PII**: ALIGNED in intent; **the enforcement mechanism as described is under-specified and, read literally, unsound.** See Logic Check #2. "PII-free by construction, enforced by serializer tests" conflates two different layers that need two different controls: (a) *field-level* PII (names, free text, precise location) — solved by construction only if the public DTO is an **allowlist projection** whose type structurally *cannot hold* those fields, with tests as the regression guard; a denylist/redaction serializer that strips known-bad fields is NOT "by construction" and leaks the next field someone adds. And (b) *statistical* re-identification (k≥5, ≥15-min buckets) — which a serializer **cannot** guarantee, because k-anonymity is a property of the *aggregation query and the population in the bucket*, not of serialization. The sound design suppresses cells with k<5 at the query layer and refuses to emit them; the serializer can only enforce that it never receives a raw row. Name both layers or minimization is asserted, not built.

- **Auditability**: NEUTRAL/ALIGNED. The board reads state; it does not author it, so it inherits the existing append-only attribution. D4 (Ver como) is actually a *positive* auditability contribution — a standing leak-audit — but only if implemented as a real audience-endpoint preview (see D4 below).

- **Crisis-grade & reversible**: ALIGNED, with a real caveat the proposal owns (risk #3): continuous animation on low-end devices degrades the primary audience's experience. The stated mitigation (static SSR snapshot first, animation as progressive enhancement) is correct and should be an *acceptance criterion*, not a mitigation footnote — the static snapshot is the product; the animation is the garnish.

## Logic Check

1. **Claim: "The honesty principle is satisfied because the animation renders REAL recorded events; any sample/demo mode is labeled."** — **Holds for the coordinator board; does NOT hold as stated for the public demo. This is the non-sequitur the Board asked me to name.** The honesty argument is built on 1:1 real-event binding and then extended to demo mode — but demo mode is *precisely* the case where the binding is suspended (synthetic motion, no real event). So the guarantee does not cover the one surface it most needs to cover: the public landing before the gate opens. Demo mode is not honest *because* animations bind to real events (they don't, in demo); it is honest *only if* the "demostración" label is unmissable and survives being screenshotted out of context. The proposal should stop citing the binding as demo mode's honesty basis and instead specify the labeling bar explicitly. **Does animated demo on the landing pre-empt the closed 007 gate?** Not in the letter — the 007 gate governs the *real aggregated feed*, and synthetic labeled data is not that feed, carries no PII, and has no targeting value (there is no real event behind it). But it pre-empts it in *spirit*: it stands up the public visual surface, trains the eye to expect a live public board, and manufactures the "system is alive" trust frame using motion the gate has specifically forbidden serving for real. That is soft pressure on a closed gate plus spectacle risk. **Occam resolves it (below): a static labeled snapshot conveys "here is the board that ships once approved" with none of the spectacle or screenshot-stripping risk. The animation adds spectacle, not information, on the pre-gate public surface.**

2. **Claim: "The public feed is PII-free by construction, enforced by serializer unit tests, not review vigilance."** — **Partially holds; the mechanism is right in spirit but wrong (or at least ambiguous) in construction.** "By construction" and "enforced by tests" are two different guarantees. Construction = the output type cannot represent a name (allowlist projection). Tests = a regression net over known cases. If the design is "serialize the domain object, test that names don't appear," that is denylist + vigilance-by-test — exactly what the proposal says it is *avoiding* — and it fails open on the next field added. And k≥5 / timing coarsening are *not serializer properties at all*; they are aggregation-and-suppression properties. The claim is achievable, but only if restated as: **typed allowlist DTO (field-level, by construction) + k-suppression at the aggregation query (statistical, by construction) + adversarial serializer/fuzz tests as the guard.** As written, "serializer tests" is doing work two layers can't do alone.

3. **Claim (D4): "Ver como is strictly a render-preview of the lower-privilege payload, never a privilege change — the cheapest standing leak-audit we can own."** — **Holds if and only if the downgrade happens server-side.** Its entire soundness rides on *where* the payload is filtered. If "Ver como público" **re-fetches through the actual public endpoint** (the allowlist feed of Logic Check #2), it is a genuine downgrade preview AND a real audit, because it exercises the same serializer the public gets — this is good and I endorse it. If it is implemented as a **client-side mask of the privileged payload** (fetch full data, hide fields in the UI), then the privileged data is already on the client, the "preview" is a fiction, it is a *leak* rather than an audit, and the proposal's own "ver-como drift" risk (#5) is realized by design. So D4's audit value is entirely *parasitic on the allowlist serializer of D1 existing as the single source of truth*: byte-identical (success criterion #4) is only possible if the preview hits the real endpoint. Make "the preview never has access to any field above the previewed audience" a tested, binding invariant, and note that pre-011 the only honest "audiences" are public-vs-coordinator (there is no real authz to fetch *as* a volunteer yet).

4. **Claim: "No new external dependencies; SVG/canvas + Remotion in-tree + keyless Leaflet."** — **Holds.** Verified against the brief's inventory (Remotion already in-tree, keyless Leaflet+Carto serving the map, /pulso prototype exists). This is genuinely additive UI on existing substrate. Good, and it means the cost of *deferring* the animation is near-zero — nothing is blocked by shipping the static version first.

## Simplest Solution

Occam strongly favors **decoupling the four pieces and shipping in principle order (information before interface), not in demo-impact order:**

1. **Now, no gate:** D5 (search, pagination parity, collapsed assignment controls), D2 (Mi tablero — local filters, shareable URL, one-tap delete, unfilterable safety banners), D3 (one-question onboarding to a pre-filtered screen). This is the actual adoption driver for the actual user and touches no PII and no closed gate.
2. **Now, behind the existing coordinator gate:** D1 coordinator board (honest real-event binding = true situational awareness) and D4 interim (public-vs-coordinator, server-side re-fetch).
3. **Public landing, now:** a **static, labeled snapshot** of the board ("así se verá el tablero público cuando se apruebe") plus honest static totals ("1,021 necesidades, 150 sitios, N confirmadas esta semana") — NOT synthetic animation. This achieves the entire stated trust goal ("system is alive, here's what it does") with no spectacle, no screenshot-stripping risk, and no soft pressure on the gate.
4. **Public animated feed:** only after the 007 re-review passes AND on top of the corrected two-layer feed contract (allowlist DTO + query-level k-suppression).

**What is lost by simplifying:** the "wow" of live public motion pre-gate. That is a marketing loss, not an information loss — and the principle in HOS's name is *information* before interfaces. A deeper cut the proposal should at least answer: does the trust/adoption *purpose* actually *require* a live per-district cadence feed, or would honest coarse static totals achieve it? If static totals build the same trust, then serving a live district-grain feed exposes *more than the minimum needed for its purpose* — which is a minimization argument against the live public feed existing at all, independent of the gate. I don't think that kills it, but the proposer should have to show that the live feed buys trust the static counts can't, before the k-anonymity/targeting-oracle machinery is worth building and defending.

## Technical Debt Created

- **Owned and acceptable:** all four pieces reuse in-tree substrate (Remotion, Leaflet, /pulso prototype, existing gate). No new infra debt. Good.
- **Latent, if the feed contract ships as "serializer tests" only:** a denylist serializer is a fail-open leak surface forever — every future field added to the domain object is one review-miss away from the public payload. Building the allowlist DTO now costs the same and removes the debt permanently. This is cheap to prevent, expensive to discover.
- **Latent, if Ver como is client-side:** a privilege bug shipped as a feature, plus a false sense of audit coverage (the team believes it has a leak-audit that is actually leaking). Bind it to the real endpoint from day one.
- **Coupling debt the proposal should name:** D1-public, D4, and the 013 companion 014's "confirmado por el responsable hace 2h" public string ALL depend on the same PII-free public serializer. Design that serializer *once*, as the single public projection, or three surfaces drift apart and each becomes its own leak audit. The Expansionist's embeddable-widget question is the same serializer again — one more reason to build the allowlist projection once and treat it as the sole public boundary.

## Confidence Score

**0.82** — why not higher: the two sharp calls (allowlist-vs-denylist construction, server-vs-client Ver como) are implementation-level and I am inferring the intended design from prose; the proposer may already mean the sound version, in which case those are confirmations, not corrections. And the decisive question "does the live public feed's *purpose* require real live data, or would static totals do" is partly an empirical trust/adoption question (User's and Researcher's territory) that I can frame on principle but not settle. Whether even a k≥5, 15-min-delayed, district-grain feed remains a usable targeting oracle is the Contrarian's call, not mine — I only note that minimization prefers the coarsest thing that meets the purpose, and someone must establish what the purpose actually requires.

## What I Don't Know

- Whether the /pulso prototype's existing serializer is already an allowlist projection or a redaction pass — decisive for how much of Logic Check #2 is "confirm" vs "rebuild." (Checkable in the code; I reasoned from the proposal text.)
- Whether static honest totals genuinely fail to build the trust the live feed promises — an empirical adoption question that would settle whether the public animated feed is worth its k-anonymity defense at all.
- Whether the "demostración" label survives HOS's real distribution channel (WhatsApp OG-card screenshots stripped of surrounding context) — a User/Researcher test, but it is the pivot on which demo-mode honesty actually turns.
- Whether the 2026-07-03 HOS-2026-008-D1 answer (which *unblocks the 007 re-review*, not the gate) has been written into the 008 log yet — the proposal flags it is in-session only. Until it is written, the re-review this whole public path depends on is not formally unblocked, and D1-public has no clean footing.
